# The demo records one capability: open_sub_account, with a balance read inside it

The brief offers "read a member's savings balance" and "open a sub-account" as example goals. A read-only capability cannot demonstrate requirement 3.4 (safe vs risky actions) or the risky-step half of 3.6 (human decides), so the demo records the write flow and reads the savings balance as an output on the way through: search → detail (read balance) → form → confirmation. One capability then exercises typed outputs, business outcomes, recoverable conditions, escalation, the Consequential Step with Operator approval, Refused-when-unattended and the Verification Check. Building order is still read-first: the flow up to the balance read is made deterministic before the form and the commit click are added. The app gets a reset endpoint so runs are repeatable.
